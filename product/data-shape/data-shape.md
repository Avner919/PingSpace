# Data Shape

## Entities

### User

Постоянно сохраняемый на сервере аккаунт человека, входящего в PingSpace по e-mail и паролю: игрока или администратора. Роль определяет доступ к собственным бронированиям или ко всему расписанию; администратор — роль аккаунта, а не отдельная сущность и не вариант публичной регистрации.

### Session

Независимая сессия входа одного браузера в аккаунт User, с ограниченным сроком действия. Браузер хранит случайный токен в HttpOnly-cookie, сервер хранит его хеш и связь с пользователем; выход завершает только соответствующую сессию.

### Location

Единственная локация для игры в Москве, Россия; задаёт местный контекст расписания, часовой пояс `Europe/Moscow`, валюту RUB и правила доступности. Работает ежедневно круглосуточно (24/7); тариф за один стол — 800 ₽/час за первые 60 минут каждой брони и 500 ₽/час за дальнейшее время с пропорциональной оплатой неполного часа. Адрес: Москва, Тверская, 11; в прототипе доступна ровно одна локация.

### Table

Конкретный стол для настольного тенниса в локации, доступный для бронирования. В целевом прототипе существует ровно три стола; доступность каждого определяется его активными бронированиями в круглосуточном расписании.

### Booking

Единая запись игрока на один, два или три выбранных стола на общий непрерывный интервал игры длительностью от 30 до 240 минут с шагом 30 минут. Хранит связь с игроком и выбранными столами, начало и окончание игры, согласованную при создании стоимость за каждый стол и общую сумму в рублях и состояние «активна» или «отменена»; для отменённой записи сохраняется, кто и когда выполнил отмену, вместо удаления записи из истории. Бронирование может переходить через полночь: начало и окончание относятся к конкретным моментам времени, а не только к часам в пределах выбранной даты.

## Relationships

- User может иметь несколько Session для разных браузеров; каждая Session относится к одному User. Аккаунт и брони сохраняются в общей серверной базе после завершения сессий и перезапуска приложения.

- Location содержит три Table; каждый Table принадлежит одной Location.
- User может иметь много Booking как игрок; каждая Booking принадлежит одному User и включает от одного до трёх Table на одно время.
- Table может иметь много Booking; активные Booking одного Table не пересекаются по времени, но могут следовать непосредственно друг за другом.
- Location связана со всеми своими Booking через Table; отдельный выбор из нескольких локаций в текущем прототипе не нужен.
- User с ролью администратора может просматривать Booking всех трёх Table и выполнять отмену; отменивший User может отличаться от владельца Booking.
- Пользовательская отмена Booking разрешена владельцу, если до начала осталось не менее 60 минут; отдельное исключение для администратора требует согласования.
- После отмены Booking остаётся связанной с владельцем и всеми выбранными Table, но освобождает интервал на каждом из них; частичная отмена отдельных столов внутри одной Booking не предусмотрена.
- Доступный временной слот — вычисляемое представление свободного интервала Table, а не отдельная сохраняемая сущность; он определяется круглосуточным режимом, выбранной длительностью и активными Booking; проверка пересечений охватывает также записи, начавшиеся в предыдущие сутки или заканчивающиеся в следующие.
- Стоимость Booking фиксируется при её создании на основе тарифа Location: `800 × min(m, 60) / 60 + 500 × max(m − 60, 0) / 60`, за каждый выбранный стол, затем суммы складываются; `m` — общая длительность в минутах; например, 30 минут стоят 400 ₽, 90 минут — 1 050 ₽, 240 минут — 2 300 ₽. Тариф считается для всей Booking и не сбрасывается при переходе через полночь; оплата предполагается в клубе, поэтому сущность онлайн-платежа и интеграция с провайдером в этой модели отсутствуют.
- Новая Booking сохраняется только при доступности всех выбранных Table; доступные слоты — пересечение свободных интервалов выбранных столов. Существующие одиночные записи остаются доступными и трактуются как Booking с одним Table.
- Время отображается и правила отмены вычисляются в контексте Location; настройки часового пояса браузера не должны менять момент начала игры и право отмены.

- Пароль User сохраняется только как scrypt-хеш с солью. Авторизация и роли определяются серверной Session; значения из браузерного localStorage не подтверждают личность и не назначают административную роль.
- Все новые Booking сохраняются сервером в серверной базе (Neon Postgres локально и в Vercel); проверка общей доступности и запись группы выполняются одной транзакцией. Чужие подробности Booking доступны только администратору; публичное расписание показывает занятость без персональных данных.
